# Performance & architecture plan — 2026-09-22

Scope: (A) app load + responsiveness, (B) calculation speed + accuracy. Every item below was
verified in source or measured; numbers come from this machine (Node 24, M-series) unless noted.
Baseline at `main` = 7f9bceb. Tests: 517 pass / 3 skipped (44 s). `tsc` fails only in the
pre-existing `profile-counts.test.ts`; lint has 2 pre-existing `set-state-in-effect` errors.

## Headline numbers

| What | Measured |
|---|---|
| Initial JS for `/` (prod build) | 1.38 MB raw / **453 KB gzip**, 15 chunks; CSS 141 KB / 23 KB gz |
| Of which: Next+react-dom runtime 642 KB raw, `@base-ui/react` 321 KB, app code ~140 KB, phosphor 63 KB, tailwind-merge 27 KB |
| Manifest item table on the wire (first visit) | 10.7 MB gz → **199 MB JSON**, 38,894 defs, parsed on the main thread |
| Cached item table read from IndexedDB **every load** | 17,223 defs, **90 MB JSON / 83 MB v8-serialized**; deserialize 360 ms in Node (browser IDB: ~1–3 s incl. disk) |
| Same table projected to the fields the app reads | ~25–40 MB (2–3.5× smaller), deserialize 170–220 ms |
| Solver, default builder query (all mins 0) | **caps at 6 s budget** (17 M leaves); 11 of 15 fixture queries cap |
| Solver with admissible-bound fixes (prototype, identical results) | default query **32 ms**; 13 of 15 queries < 220 ms |

The two largest wins are unrelated to UI code: the solver's top-N bound is loose, and the manifest
cache is 10× bigger than it needs to be and sits on the critical path serially with three other
network legs.

## Phase 1 — Solver: make the default query finish in milliseconds (pure speed, provably identical results)

**Status (2026-09-22): landed on branch `perf/solver-bounds`** as six commits: bench + result-hash gate
(`scripts/optimizer-bench.ts`, `verify` mode, snapshot from 7f9bceb), mod-slack bound (1.1 + 1.5),
exotic child-skip (1.2), tuning-upside tightening (1.4), plain-minus dominance (1.3), and a second
admission bound (net tuning credit + signed fragments + pool-wide zero-clamp slack) found while
landing — it fixed an all-six-minimums-with-fragments query that the four planned changes left capped.
Every step was byte-identical on the 18-query hash gate; new tests: total-bound admissibility (both
bounds, brute-forced completions), `assignMods` overshoot ≤ 9, exotic-skip `combosTried` pin, and
`tuner-exhaustive.test.ts` (unpruned walk of the tuner's tree must return the identical leaf; a
mutation check confirmed it catches a broken plain-minus rule). Real pool, production budgets, after:

| Query | before | after |
|---|---|---|
| loose (default) | 6 s cap | 8 ms |
| weapons ≥200 / health ≥100 | 6 s cap | 89 / 41 ms |
| 150/150, 120/100/100, specific-exotic 150/150, no-exotic 150/150 | 6 s cap | 5–18 ms |
| six stats ≥70 + mixed fragments | 6 s cap | 32 ms (ceilings still inexact at 1.2 s) |
| two-set fixture | 1.9 s, ceilings inexact | 0.3 s walk; ceilings exact in 1.05 s, still inexact under the 1.2 s fair-share scheduling |
| CODA 4pc | 0.4 s | 53 ms |
| power range loose / 150-150 | 6 s cap | 4 / 9 ms |
| artifice pools | 6 s cap | still cap (see Not now) |

Remaining, not in this branch: ceiling probe scheduling (fair shares abort probes that would finish
inside the total budget — the two-set fixture proves exact in 1.05 s but reports inexact at 1.2 s),
and the artifice/legacy pool bounds.

Prototype measured in `/tmp/optbench` against the 496-piece real Warlock fixture with production
budgets (6 s top-N, 1.2 s ceilings). Every completed comparison was bit-identical in build set,
ranking, ceilings, and upper bounds. The copied optimizer test suite (126 tests incl.
`completeness-oracle`, `bound-admissibility`) passes against the prototype.

| # | Change | Where | Effect (measured) | Exactness risk |
|---|---|---|---|---|
| 1.1 | **Mod-slack bound.** Credit `modUpside = min(maxModPoints, Σ_{min[s]>0} (min(200, min[s]+9) − lowerBound(have[s])))` instead of flat `maxModPoints`. | 1.2 | **Exotic child-skip.** Under `exotic: require`, skip children when no exotic chosen yet and `exoticSuffix[k+1] === 0`. Today 99.7 % of two-set leaves (736,838 / 739,490) are rejected *after* descending 4 slots (`solve.ts:255`); ceiling probes waste 58.9 M depth-4 nodes the same way. | `solve.ts:317` (recurse loop), `ceilings.ts:171-183` | two-set to exact ceilings 6.0 s → **0.83 s**; inline 1.2 s ceilings become exact | none |

| 1.4 | **Tuning-upside tightening.** `tuneTotalUpside` (`tuning.ts:194-195`) credits +5 per directional; a directional nets +5 only if its −5 is clamp-absorbed. ## Phase 2 — Startup: collapse the serial waterfall

Today (all serial, `use-session.ts:47` → `use-manifest.ts:32` → `load.ts:120-131` → `use-armory.ts:23` → `fetch.ts:89` → 250 ms debounce → worker spawn):

```
HTML → 453 KB JS → hydrate → GET /api/auth/session → GET bungie /Manifest/ (version RTT)
  → IDB open + 11 gets (83 MB deserialize) → GET /api/bungie/profile → normalizeArmory (main thread)
  → 250 ms debounce → new Worker + fetch worker chunk → solve (6 s today)
```

| # | Change | Where | Why / size |
|---|---|---|---|

## Not now / deliberately deferred

- **Artifice / legacy pools still cap** after Phase 1 (72 M leaves; 150/150 completes in 109 s vs >300 s). The `(chosenArt.n + artSuffix[k]) * 3` credit and flat synthetic legacy pieces admit huge tie plateaus. Needs its own bound work; Pareto pre-filtering (`bounds.ts:21` caveat) would finally apply there. Revisit when legacy armor is enabled by default.
- Resumable search / pool-by-id worker / typed arrays / slot reordering: no measured need after Phase 1.
- Persisting React Query wholesale (persister) — persist only the normalized `Armory` (2.5); the manifest already has its own cache.
